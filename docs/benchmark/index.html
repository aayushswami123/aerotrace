What does a C change break? Four tools, 30 changes: 27 checked against the compiler, 3 by hand.

Easy cases (9): every tool found all 25 breaks. Hard cases without the macro case curl-09 (17): AeroTrace found 91 of 95 with 0 false alarms; clangd 95 with 8, cscope 95 with 60, ripgrep 95 with 74.

In one line: AeroTrace did not beat clangd here. On the 13 hard cases where AeroTrace named at least one break, both score the same (91 of 91 found, 0 false alarms each). AeroTrace's lower false-alarm count against clangd comes from cases where it named no break at all. Against cscope and ripgrep it has fewer false alarms there (0 against 51 and 65). It found fewer breaks than another tool in 5 of 27 build cases, and it takes 329 ms to 6.3 s per check where the others take at most 81 ms.

A wrong "safe" answer in 4 cases. In redis-05, redis-07, curl-05, curl-07 the build fails, but AeroTrace's answer says "None is sure to break". That is the worst kind of answer by AeroTrace's own rules. It is a product bug, reported, not fixed in this run. A fix (#77) has since been merged into launch-candidate; it is not measured here. In curl-09, which breaks 344 functions, its answer opens with "Nothing found that this change can break, but 2 parts of the change could not be followed." It does say what it couldn't see, so the rules don't count it as a wrong "safe" answer, but an agent that reads only that line is misled.

Each tool was asked the question an agent asks before an edit, the way the tool is normally used. 27 changes were scored against what the compiler and linker report; the other 3, which build fine, against callers checked by hand.

The macro case curl-09

A function-like macro in a header gets a new parameter. It is used inside other macros, so the compiler reports 344 functions. Found: AeroTrace 0, clangd 4, cscope 4, ripgrep 4. clangd, cscope and ripgrep point at the macro definitions that cause it, which the rules don't count as breaks. AeroTrace says it couldn't follow the change. Shown apart so one case doesn't decide the headline.

How each tool was run. AeroTrace: claimed breaks from `aerotrace check --patch case.diff --json`. clangd: find-references at the symbol's definition (background index). cscope: `cscope -d -L0 <name>` (find this C symbol). ripgrep: `rg -n -w <name>` over the build's files. Truth: each patch applied to a built copy of the pinned release, rebuilt with every error reported; every compile and link error is a break. A break is counted per function (or table).

Versions. aerotrace 0.1.0.dev0 (analysis code as of commit eff898b), Apple clangd version 21.0.0 (clang-2100.1.1.101), cscope: version 15.9, ripgrep 15.2.0. Compiler: Apple clang version 21.0.0 (clang-2100.1.1.101). Machine. Apple M1 Pro, macOS 26.7.2, arm64. Time is the median of 3 runs per query; one-off setup:

  • Redis: AeroTrace index 5.5 s, clangd index 2.2 s, cscope database 0.4 s
  • SQLite: AeroTrace index 4.8 s, clangd index 0.8 s, cscope database 0.5 s
  • curl: AeroTrace index 5.6 s, clangd index 4.8 s, cscope database 0.4 s

Read with care. The 27 build changes are edits we made, of 10 kinds we chose, scored by rules we wrote before any tool ran; most have only 1 to 25 breaks. The link step ran in 4 of them; in the others the build stopped at compile errors, so link-only breaks are not in the truth. AeroTrace's time is a new uv run aerotrace check process each time (Python start-up included; the running MCP server was not timed). clangd's is one query to a running, indexed server, asked at the symbol's definition, which an agent first has to find. cscope was asked -L0 (every use of the symbol); -L3 (callers only) would list fewer prototypes and was not run.

Tool errors (counted as misses): AeroTrace 0, clangd 0, cscope 0, ripgrep 0.

The MCP text of AeroTrace's answer shows at most 15 items per list; in redis-04 (2), redis-06 (10), sqlite-04 (4) it hides that many claimed breaks behind "N more". Recall is scored on the full answer.
